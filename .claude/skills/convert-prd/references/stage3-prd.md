# Stage 3: Convert_to_PRD (raw requirements → PRD v1)

> ต้นฉบับจาก `Convert to PRD.md` (ทำความสะอาดเครื่องหมาย escape แล้ว เนื้อหาไม่เปลี่ยน)
> `RAW SUMMARY` คือไฟล์ raw requirements จาก Stage 2 ส่วน `PRD TEMPLATE` อยู่ที่ [prd-template.md](prd-template.md) ให้ใช้หัวข้อตรงตัวตามนั้น

## TASK

ให้นำ raw requirements summary จากด้านบนมาจัดทำเป็น PRD v1
โดยใช้ template ที่ฉันจะให้ด้านล่าง

## STEPS

1. นำ Problems / Goals / Users / Use Cases / FR / BR จาก summary
   ไปจัดลงใน section ที่ถูกต้องของ PRD template
2. กำหนด ID ดังนี้:

- PRD-ID: PRD-<CODE>-001
- FR-IDs: FR-<CODE>-00X
- UC-IDs: UC-00X
- FLOW-IDs: FLOW-<CODE>-00X
- AC-IDs: AC-<CODE>-00X

(หมายเหตุ: ในไฟล์ต้นฉบับ ส่วน `<CODE>` หายไปจากการแปลงรูปแบบ เหลือเป็น `PRD--001` ให้ใช้รหัสโปรเจกต์สั้น ๆ ตัวพิมพ์ใหญ่ที่ได้จากชื่อ Product เช่น AI Hub → `AIHUB` ถ้าผู้ใช้ไม่ระบุให้ตั้งเองและบันทึกใน Assumptions)

3. สำหรับแต่ละ Functional Requirement:

- เขียนว่า ระบบต้องทำอะไร (WHAT) ในความยาว 1-3 ประโยค
- อ้างอิงกลับไปยัง Use Cases และ Problems ที่เกี่ยวข้องด้วย ID

4. สำหรับแต่ละ FR ที่สำคัญ:

- เสนอ Acceptance Criteria จำนวน 1-3 ข้อ ในรูปแบบ Given / When / Then
- ให้ใส่เครื่องหมาย [DRAFT] ถ้าสิ่งนั้นไม่ได้ถูกระบุไว้อย่างชัดเจนใน input

5. หากมีข้อมูลที่ตกหล่น หรือยังไม่ชัดเจน
   ให้นำไปไว้ในหัวข้อ Open Questions

## RULES

- ห้ามสร้างฟีเจอร์ใหม่ที่ไม่มีอยู่ในข้อมูลต้นทาง ทั้งแบบระบุชัดเจนหรือโดยนัย
- ถ้าจำเป็นต้องมีการสมมติ ให้ระบุอย่างชัดเจนไว้ในหัวข้อ Assumptions
- ใช้หัวข้อใน PRD template ตามต้นฉบับแบบตรงตัว

## แนวทางเพิ่มเติมจากการใช้งานจริง (ไม่ใช่ส่วนของ prompt ต้นฉบับ)

**ID ที่ต้องเติมเอง**
- ปัญหา (Problems) ใน raw requirements มักไม่มี ID ให้กำหนด `P-001...` ในหัวข้อ 2 เพื่อให้ FR อ้างอิงได้ และบันทึกใน Assumptions ว่าเป็น ID ที่เพิ่มเอง การจับคู่ FR กับ Problem เป็นการเชื่อมโยงของผู้จัดทำ ไม่ได้มาจากที่ประชุม
- Business Rules ใช้ `BR-<CODE>-00X`, Open Questions ใช้ `OQ-001...`, Assumptions ใช้ `A-001...`

**การเขียน FR**
- รวม FR-R ที่เป็นเรื่องเดียวกันเป็น FR เดียวได้ แต่ทุก FR-R ต้องมีที่ลงใน PRD ห้ามตัดทิ้ง
- FR ที่ไม่มี UC หรือ Problem ที่ผู้พูดผูกไว้โดยตรง ให้เขียน "ไม่มี UC ที่ระบุโดยตรง" / "ไม่ระบุ" แทนการแต่งความเชื่อมโยง
- ห้ามเพิ่มพฤติกรรมโดยนัย เช่น input บอกแค่ "Dark Mode เป็นค่า Default" ห้ามเขียนว่ามีปุ่มสลับ Light/Dark ให้ยกเป็น Open Question

**Acceptance Criteria**
- AC เป็นข้อเสนอของผู้จัดทำทั้งหมด ใส่หมายเหตุต้นหัวข้อ 14 และใส่ `[DRAFT]` ทุกข้อที่มีรายละเอียดเกินกว่าที่ input ระบุ พร้อมอ้างอิง OQ ที่เกี่ยวข้อง
- ทุก FR ต้องมี AC อย่างน้อย 1 ข้อ ใช้เลขต่อเนื่อง `AC-<CODE>-001, 002, ...` และระบุ "(สำหรับ FR-<CODE>-00X)"

**ตรวจก่อนส่งมอบ**
- Business Rules ต้องไม่ขัดกันเอง หรือขัดกับ FR (เช่น "CTA ทุกตัวไป Sign-up" กับ "View Documentation เปิดได้โดยไม่ต้องล็อกอิน") ถ้าขัดกันให้ใส่ใน Open Questions ห้ามตัดสินเอง
- ทุก UC ถูกอ้างอิงโดยอย่างน้อย 1 FR
- Out-of-scope ตรงกับ Non-goals และ Success Metrics ที่ไม่มีตัวเลขให้เขียน "ไม่ระบุ"
- สถานะ `Draft`, Owner "ไม่ระบุ" ถ้า input ไม่มี, วันที่อัปเดตล่าสุดใช้วันที่ปัจจุบัน
- Open Questions ให้รวม `[AMBIGUOUS]` ทั้งหมดจาก input จัดกลุ่ม: ที่ประชุมยังไม่ตัดสินใจ / คำถอดเสียงที่ไม่แน่ใจ / ข้อมูลไม่ครบ / ประเด็นเพิ่มเติมที่พบระหว่างทำ PRD
